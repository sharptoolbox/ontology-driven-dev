# 本体模型业务功能开发指导书

> 基于 `code-paas`（系统管理 + 流程引擎技术底座）扩展新业务功能的标准开发规范
> 版本 1.2 · 对齐《AI 原生应用技术架构设计文档》《UI-UE 界面设计规范》《本体驱动软件建模方案 v9.0》《系统管理 + 流程引擎需求规格说明书》

---

## 0. 文档目的与读者

本文档回答一个问题：**拿到一个全新的业务本体模型（M1/M2/M3/M5/M6/M7/MU），如何在 `code-paas` 技术底座之上，完整、规范、可运行地落地成一套业务功能。**

读者为：负责基于本体模型做增量开发的 AI 助手与开发人员。

核心约定（贯穿全文）：

1. **底座不动**：`code-paas` 是只读的技术底座，新功能一律在 `code-app` 中开发（先整体复制一份）；
2. **模型是唯一语义来源**：所有表、接口、页面、菜单、权限、流程、规则都必须能回溯到某个本体模型元素，禁止"模型一套、代码一套"；
3. **遵循两大规范**：开发过程完全遵守《AI 原生应用技术架构设计文档》与《UI-UE 界面设计规范》；
4. **UI 输入唯一**：《UI-UE 界面设计规范》是唯一设计事实源，复制到 `code-app` 的技术底座是唯一实现起点；开发资料不提供、开发过程不得寻找或依赖任何 `UI原型`、`demo-default` 或其他 Demo 源代码；
5. **AI 原生**：新功能必须实现右侧 AI 对话框的自然语义对话能力（本文第 7 章）。
6. **基础菜单保护**：审批中心、流程管理与系统管理是底座不可删除的一级菜单，相关路由、后端模块和 `sys_resource` 种子必须保留。审批中心必须包含“待我审批”与“我已审批”，是 M6 审批任务的统一入口；系统管理员登录时必须从元数据展示全部启用的底座默认菜单与当前模型菜单；其他用户按角色权限展示，不得以静态前端菜单绕过鉴权。
7. **业务边界**：底座仅保护审批中心、流程管理和系统管理，不预置客户管理或其他业务领域功能；客户管理是否生成由当前需求说明书与本体模型决定。审批中心属于通用技术能力，不属于经营中心/经营工作台或业务领域功能。底座不注入经营中心/经营工作台菜单，新系统仅保留不含业务指标、图表、列表和快捷入口的空白首页。

## 1. 从 code-paas 到 code-app

### 1.1 复制与隔离（强制）

新功能开发**严禁直接修改 `code-paas`**。若导出的开发包已提供 `应用源码/code-app/`，该目录就是已复制完成的唯一可写应用源码，直接在其中开发，禁止再次复制或修改技术底座。只有单独取得技术底座源码、且尚未存在 `code-app` 时，才执行以下复制命令：

```powershell
# 在项目根目录执行（Windows PowerShell）
Copy-Item -Path ".\code-paas" -Destination ".\code-app" -Recurse
```

后续所有扩展都在 `code-app` 内进行。`code-paas` 保持原样，作为底座基线，便于回退与对照。

复制后需要清理的临时产物（可选但建议）：

```powershell
Remove-Item -Recurse -Force .\code-app\backend\data          # 数据库，首次启动自动重建
Remove-Item -Recurse -Force .\code-app\backend\__pycache__ -ErrorAction SilentlyContinue
Remove-Item -Recurse -Force .\code-app\frontend\node_modules # 重新 npm install
Remove-Item -Recurse -Force .\code-app\frontend\dist
```

### 1.2 技术底座"已提供什么" vs "要扩展什么"

| 能力 | 底座现状（code-paas 已提供） | 扩展新功能时需要做的 |
|---|---|---|
| 登录/认证 | JWT 登录、`admin` 默认账号 | 无需改动（可新增业务账号） |
| 系统管理 | 用户/角色（继承）/权限（行为级+数据范围）/资源（菜单·按钮·接口）CRUD | 启动时按 M5/MU 幂等同步角色、权限、授权关系和菜单资源 |
| 流程引擎 | `flow_definition/instance/task/history` + 引擎 `start/approve/reject/return` | 启动时按 M6 幂等同步 `flow_definition`（nodeGraph） |
| 审批中心 | 待我审批、我已审批、转办/催办/退回 | 必须保留；M6 审批任务统一从“待我审批”进入处理 |
| 本体注册表 | `ontology/registry.py` 加载 `models/` 下 YAML | 新增/修改 `models/*.yaml` 并加入 `manifest.json` |
| 业务领域功能 | 底座不预置客户管理或其他业务领域页面、数据和接口 | 仅按当前需求说明书与本体模型生成；客户管理不受底座限制 |
| 经营工作台 | 底座不注入经营中心/经营工作台菜单 | 首页仅保留空白容器 |
| AI 对话 | 右侧对话布局与扩展接口 | 按第 7 章在系统管理的“配置大模型”页面维护 `ai_config` 后实现 |

## 3. 关键约定与规范（强制）

### 3.1 编号自动生成规则

> 业务对象"编号"字段一律由系统自动生成，界面**不显示、不可编辑**（若需展示也只读）。

规则：**对象英文别名（alias）大写取前 3 位 + 4 位流水号**。

| 对象 alias | 前缀 | 示例 |
|---|---|---|
| Contract | `CON` | `CON0042` |
| Invoice | `INV` | `INV0107` |
| Receipt | `RCP` | `RCP0003` |
| Product | `PRD` | `PRD0012` |

参考实现（`backend/utils/codegen.py`，在**同一事务内**生成，避免并发重号）：

```python
import re
import db

def generate_code(alias: str, table: str, column: str = "xxx_no", conn=None) -> str:
    """对象英文别名前 3 位大写 + 4 位流水号，如 Contract -> CON0001"""
    prefix = re.sub(r"[^A-Za-z]", "", alias).upper()[:3]
    row = db.query_one(
        f"SELECT MAX({column}) AS mx FROM {table} WHERE {column} LIKE ?",
        (f"{prefix}%",),
        conn,
    )
    cur = 0
    if row and row["mx"]:
        m = re.match(rf"^{prefix}(\d+)$", row["mx"])
        if m:
            cur = int(m.group(1))
    return f"{prefix}{cur + 1:04d}"
```

> 正式扩展开发一律采用本节的“三位前缀 + 四位流水号”规则。

### 3.2 数据库表 5 个默认字段约定（强制）

任何新建业务表，除业务字段外，**必须追加以下 5 个默认字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `created_by` | INTEGER | 创建人（用户 ID） |
| `created_at` | DATETIME DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| `updated_by` | INTEGER | 更新人（用户 ID） |
| `updated_at` | DATETIME DEFAULT CURRENT_TIMESTAMP | 更新时间 |
| `flag` | TINYINT DEFAULT 1 | 数据有效标志（1 有效 / 0 逻辑删除） |

约束：

1. 这 5 个字段**不显示在界面表单上**，由后端 service 在数据写入时**自动赋值**：
   - `created_by` / `updated_by` = 当前登录用户 `g.user_id`（经 `auth_service.current_user()` 获取）；
   - `created_at` 由 DB 默认值写入；`updated_at` 每次更新显式 `CURRENT_TIMESTAMP`；
   - `flag` 新增默认 1；删除采用**逻辑删除**（`flag=0`），不做物理删除。
2. 查询列表默认只返回 `flag=1` 的数据（`WHERE flag=1`）。
3. 该约定与架构文档 §11.2 的映射策略并行：聚合根→主表、子实体→从表，主从表都带这 5 个字段。

参考 DDL：

```sql
CREATE TABLE IF NOT EXISTS contract (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    contract_no  VARCHAR(50) UNIQUE NOT NULL,   -- 系统自动编号
    contract_name VARCHAR(100) NOT NULL,
    -- ……业务字段……
    status VARCHAR(30) DEFAULT '草稿',
    created_by INTEGER,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_by INTEGER,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    flag TINYINT DEFAULT 1
);
```

### 3.3 控件类型映射规则（强制，对齐 MU §8.3）

| M1 属性类型 | 界面控件 | 说明 |
|---|---|---|
| Date / DateTime | `DATEPICKER`（`type="date"`） | 日期控件 |
| Enum | `COMBO`（下拉框） | 选项来自 `enumValues` |
| DictionaryRef | `COMBO`（下拉框） | 选项来自数据字典（label 显示、code 存储） |
| **AggregateRootRef** | **`POPUP_SELECT`（跳选框）** | 文本框 + 右侧按钮弹窗选择 |
| Boolean | `CHECKBOX`（`type="checkbox"`） | 复选框 |
| String（长文本/备注） | `TEXTAREA` | 多行文本域 |
| Integer/Decimal/Money | `NUMBER`（`type="number"`） | 数字框 |
| 其它 String | `TEXTBOX` | 文本框 |

要点：

- **对象引用（AggregateRootRef）必须用跳选框**：点击弹出目标对象的选择列表（分页 + 关键字），选中后回填显示名与 ID；
- **枚举 / 数据字典必须用下拉框**；
- 下拉框数据来源：枚举用 `enumValues`；数据字典经注册表 `/api/meta/dictionaries` 返回。

### 3.4 数据字典自动注册

M1 中 `data_dictionaries` 里配置的字典项，由 `ontology/registry.py` 在启动时解析进 `registry["data_dictionaries"]`，前端经 `/api/meta/dictionaries` 获取即可渲染下拉框，**无需手工再建字典数据**。

> 若字典项需要在运行期维护（增删改），再扩展字典维护功能；建模期配置的静态字典项默认只读生效。

### 3.5 主从表单：单事务 + 从表外键自动赋值（强制）

主从表（`MASTER_DETAIL_FORM`）保存必须满足：

1. **同一事务**：主表 insert + 从表批量 insert/delete 在**一个 `db.transaction`** 内完成，任一失败整体回滚；
2. **从表外键自动赋值**：先插入主表拿到主键 `master_id`，再为每个从表行自动写入 `{master}_id = master_id`（从表外键不在界面上让用户填写）；
3. **从表全量重建**：更新时按主表主键先逻辑删除（`flag=0`）或物理删除旧从表行，再按当前提交的行重新插入，保证与界面行一致。

参考实现：

```python
def save_with_details(master, details, user):
    def _do(conn):
        master["xxx_no"] = generate_code("Contract", "contract", "contract_no", conn)
        mid = db.execute(
            "INSERT INTO contract (contract_no, contract_name, ..., created_by, updated_by) VALUES (?,?,?,?,?)",
            (master["contract_no"], master["contract_name"], ..., user["id"], user["id"]),
            conn,
        )[0]
        for d in details:
            db.execute(
                "INSERT INTO contract_stage (contract_id, stage_name, ..., created_by, updated_by) VALUES (?,?,?,?,?)",
                (mid, d["stage_name"], ..., user["id"], user["id"]),   # 外键自动 = mid
                conn,
            )
        return mid
    db.transaction(_do)
```

### 3.6 规则模型完整实现要求（强制）

> 用户要求：规则模型中的规则必须**完整实现**，不允许只建模不落地。

规则分三层落地，都必须真实生效：

| 层级 | 模型位置 | 落地方式 | 触发时机 |
|---|---|---|---|
| 属性级 | M1 `attributes[].refRules` | service 保存时逐字段校验 | 保存/提交前 |
| 聚合级 | M1 `invariants` | service 保存时聚合内校验 | 保存/提交前 |
| 跨对象级 | M3 `rules[]` | 规则引擎统一求值（`simpleeval`） | 行为执行中（appliedRules）或 syncTriggers 条件 |

参考实现（规则引擎，`backend/utils/rules.py`）：

```python
from simpleeval import simple_eval

def evaluate_rule(expression: str, params: dict):
    """执行 M3 规则表达式，返回布尔或结果值。params 由 inputParams 映射。"""
    return simple_eval(expression, names=params)

def check(rule, params):
    """校验规则，不满足则抛业务异常（带 violationMessage）。"""
    ok = evaluate_rule(rule["expression"], params)
    if not ok:
        raise ValueError(rule.get("violationMessage") or f"规则 {rule['name']} 校验不通过")
```

service 内调用示例（对应 M2 的 `appliedRules`）：

```python
from utils.rules import check
from ontology.registry import registry

def submit(record_id, user):
    # ... 前置校验
    rule = registry["rules"].get("RULE-XXX-ELIGIBLE")
    if rule:
        check(rule, {"recordId": record_id, "amount": record["amount"]})
    # ... 状态变更
```

> `M1 refRules`/`invariants` 若用简单表达式表达，同样走 `simple_eval`；若表达式复杂（含聚合内求和等），在 service 内写等价 Python 逻辑并保证语义一致。**规则失败必须给用户明确的中文提示。**

### 3.7 权限码与资源约定

- 权限码命名：`{域}:{对象}:{动作}`，如 `contract:save`、`contract:submit`、`system:user:add`；
- 行为级权限码写在 M5 `permissions[].permissionId`，并同时出现在 M2 `requiredPermissions`；
- 菜单级资源 `permission_code` 控制菜单可见性（如 `contract:query`）；系统/流程类菜单用 `system:manage` / `flow:manage`，仅 admin 可见；
- 后端写接口用 `@require_permission('contract:submit')` 保护；admin 角色（`code=admin`）返回 `*` 通配放行。

### 3.8 API 约定与统一响应

- 前缀 `/api`；分页参数 `page`（默认 1）、`size`（默认 10）；
- 统一响应：`{ success, message, data, errorCode, traceId }`；
- 业务异常统一抛 `ValueError`，由全局错误处理器转成 `{ success:false, message }`；
- 写接口一律 `login_required` + `require_permission`。

### 3.9 前端页面约定

- 三栏布局、最小 `12px` 字体、标签右对齐控件左对齐、扁平卡片（圆角不超过 6px）、品牌蓝 `#2266e3`，复用 `frontend/src/styles/index.css`；
- 布局规则（UI-UE 规范 §7）：单表 2 列、主从主表 3 列 + 从表表格、查询条件 3 列 + 结果表格分页；
- 复用 `Modal`、`Pagination`、`toast`、`Badge`、`MenuIcon`、`statusBadge` 等组件；
- 字典、分类、类型、参数等简单基础数据维护，以及基础主数据维护功能，必须采用“列表页 + 新增/修改弹窗”的交互结构；新增和修改必须复用同一个 `Modal` 表单，通过模式、标题、初始值和提交行为区分新增与修改，禁止分别实现两套重复表单；
- 页面放在 `pages/{域}/`，接口封装放 `api/{域}.ts`，路由在 `router/index.tsx` 注册。
- 界面开发先建立“UI/UE 规范条款 → 底座组件/CSS → 业务页面”的映射，禁止以缺少 Demo 为由自行创建另一套布局和视觉样式。
- 基础菜单必须由 `seed.py` 幂等写入并通过 `sys_resource`、`sys_role_resource` 权限元数据返回；管理员从元数据获得全部启用的审批中心、流程管理、系统管理及其子菜单。前端不得静态兜底菜单，避免普通用户绕过资源授权看到受限入口。

## 4. 开发流程详解（步骤 1～10）

### 步骤 1：编写本体模型 YAML

在 `code-app/models/` 编写/扩展七个模型。建模顺序建议（参考框架 §10.1）：

`M1 对象 → M5 角色 → M3 规则 → M2 行为 → M7 查询 → M5 权限 → M6 流程 → MU 界面`。

YAML 结构与字段语义严格对齐《本体驱动软件建模方案 v9.0》，可直接参照 `yaml-new/` 与 `code-app/models/` 中已有文件。

### 步骤 2：注册到 manifest 与注册表

将新增/修改的模型文件登记进 `models/manifest.json` 的 `model_files`：

```json
{
  "model_type": "MANIFEST",
  "version": "1.0",
  "domain": "销售合同执行管理",
  "project": "contract-management",
  "model_files": [
    "m1-object-model.yaml",
    "m2-behavior-model.yaml",
    "m3-rule-model.yaml",
    "m5-actor-model.yaml",
    "m6-flow-model.yaml",
    "m7-report-model.yaml",
    "mu-ui-model.yaml"
  ]
}
```

`ontology/registry.py` 启动时按 `model_type` 分派注册（OBJECT/BEHAVIOR/RULE/ACTOR/FLOW/REPORT/UI）。**若新增了 M3 规则模型，需确认 registry 已把 `rules[]` 注册进 `registry["rules"]`（框架文档已定义该结构，`_register` 已覆盖 RULE 分支，如需可补齐）。**

### 步骤 3：M1 → 数据库表生成

在 `schema.sql` 追加业务表 DDL：

- 聚合根 → 主表；子实体（`ONE_OR_MORE`）→ 从表（外键 `{master_alias}_id`）；
- 每个字段按 §2.1 映射为 SQL 类型；
- `required` → `NOT NULL`；`unique` → `UNIQUE`；
- 追加 5 个默认字段（§3.2）。

### 步骤 4：数据字典自动注册

M1 字典无需额外代码，启动即生效。前端通过 `metaApi.dictionaries()` 取用。

### 步骤 5：M2 行为 + M3 规则 → service 实现

- 每个 COMMAND 行为 = `services/{域}_service.py` 一个方法（事务内）；
- 方法内：前置校验（preconditions）→ 规则校验（appliedRules，§3.6）→ 状态变更（postconditions）→ syncTriggers 联动；
- 每个 QUERY 行为 = 一个读方法（或走 M7）。

### 步骤 6：M5 → 系统管理配置

在 `seed.py` 的模型同步逻辑中保持幂等配置；不得仅在文档中约定或仅在空库初始化时写入：

1. 角色 `sys_role`（`code=roleId`，`parent_id` 表达继承）；
2. 权限 `sys_permission`（`code=permissionId`，`target_type/target_ref/data_scope`）；
3. 角色-权限 `sys_role_permission`；
4. 角色-资源 `sys_role_resource`；菜单资源见步骤 8。

> 注意：每次启动均按模型元素编码执行新增或更新，已存在数据库不得阻断模型更新。仅更新模型派生的元数据，不删除底座默认资源或人工维护的用户数据。

### 步骤 7：M6 → 流程引擎配置

在 `seed.py` 的 `_ensure_flow_definition` 中，由 registry 的 `flows` 幂等写入并更新 `flow_definition`。核心是把 M6 的 `activities + branches` 转成 `node_graph`（nodes + edges），审批动作结果必须写入流程变量以驱动网关分支；每个 END 必须明确 `APPROVED`、`REJECTED` 或 `RETURNED`，并按 `stateWriteBacks` 落实业务状态回写。必须复用现有流程引擎，不能只保留业务状态字段。审批流配置细节见第 6 章。

### 步骤 8：MU → 菜单 + 前端页面

1. 菜单：启动时把 MU `application.menus` 幂等写入 `sys_resource`（`DIRECTORY`/`MENU`），`MENU.path` 使用稳定路由（默认 `/app/{screenRef}`），`MENU.permission_code` 取屏幕操作权限，`icon` = lucide 图标名；再写入 `sys_role_resource`。不得替换、删除或禁用底座的审批中心、流程管理、系统管理及其默认资源种子；
2. 前端：按 `screenType` 新建页面（单表/主从/查询），按钮绑定 `actions[].behaviorRef` 对应 API；审批处理必须从“审批中心 → 待我审批”取得任务上下文再进入审批详情，不能创建绕过任务归属校验的独立审批入口；系统管理员以通配权限获得全部启用菜单，普通用户从登录返回的元数据菜单渲染，不得静态补齐菜单；
3. 路由：`router/index.tsx` 为每个 `MENU.path` 增加 `<Route path="..." element={<Xxx />} />`，确保登录后点击模型菜单可直接进入页面。

### 步骤 9：实现 AI 对话

见第 7 章。

### 步骤 10：联调与验收

按附录 A 检查清单逐项核对；用 `backend/smoke_test.py` 的方式（或 Postman）走通"录入→暂存→提交→审批→查询"全链路。

## 5. 系统管理与流程引擎的模型驱动配置

### 5.1 M5 主体模型 → 系统管理

目标：把 M5 的 actor/role/permission 落地为 `sys_*` 表，并让登录、鉴权、菜单自动生效。

**示例（新增"财务经理"角色及其审批权限）：**

M5 YAML：

```yaml
roles:
  - roleId: ROLE-FINANCE-MANAGER
    name: 财务经理
    inheritsFrom: [ROLE-FINANCE]
    permissions:
      - PERM-CONTRACT-APPROVE-FINANCE
permissions:
  - permissionId: PERM-CONTRACT-APPROVE-FINANCE
    targetType: BEHAVIOR
    targetRef: Contract_ApproveFinance
    dataScope: ALL
```

落地：

1. `sys_role`：`(name='财务经理', code='ROLE-FINANCE-MANAGER', parent_id=<ROLE-FINANCE 的 id>)`；
2. `sys_permission`：`(code='PERM-CONTRACT-APPROVE-FINANCE', target_type='BEHAVIOR', target_ref='Contract_ApproveFinance', data_scope='ALL')`；
3. `sys_role_permission`：关联该角色与该权限；
4. `sys_user_role`：把某个用户（如 `fm_user`）绑定到该角色。

效果：

- 登录后 `auth_service.get_permission_codes` 会递归父角色，汇总出该用户的权限码集合；
- `@require_permission('PERM-CONTRACT-APPROVE-FINANCE')`（或你的业务权限码）即可保护审批接口；
- 菜单可见性由 `get_menus` 按 `resource.permission_code` 过滤。

> 角色继承（`inheritsFrom`）落地为 `sys_role.parent_id`；`auth_service.get_user_roles` 已实现向上递归，无需改代码。

### 5.2 M6 流程模型 → 流程引擎

目标：把 M6 的 flow 落地为 `flow_definition`，让提交后能自动启动实例、逐节点审批。

M6 → node_graph 的转换规则（已在 §2.5 给出对照）：

- 每个 `activity` → 一个 node（`id=activityId`, `type` 映射见下）；
- 每个 `nextActivities` → 一条 edge（`source=当前`, `target=后继`）；
- 审批节点的不同结果，通过**边上的 `approval_outcome`** 区分（APPROVE/REJECT/RETURN）；
- `END` 节点用 `result` 标注 `APPROVED` / `REJECTED`，引擎据此把实例置为"通过/驳回"。

activityType → node.type 映射：

| M6 activityType | node.type |
|---|---|
| START | `start` |
| END | `end` |
| USER_TASK | `user_task` |
| APPROVAL_TASK | `approval_task` |
| SYSTEM_TASK | `system_task` |
| BEHAVIOR_CALL | `behavior_call` |
| SUB_FLOW_CALL | 仅兼容历史模型；新的正向 M6 不使用 |
| GATEWAY | `gateway` |

## 6. 工作流审批功能的完整实现（端到端）

以一个带审批的新业务功能为例，说明与流程引擎的配合方式。

### 6.1 审批对象与状态机

在 M1 中定义对象生命周期状态（如 `lifecycle: [草稿, 待财务经理审批, 待总经理审批, 已通过, 已驳回]`），并在业务表建 `status` 字段。

### 6.2 定义 M6 审批流（见 §5.2）

`flowType=APPROVAL`，`trigger.triggerType=BEHAVIOR`、`trigger.behaviorRef=Contract_Submit`（提交行为即流程入口）。

> 仅实现 M6 已建模的 `APPROVAL` 审批流。需求说明书中的端到端协同流（`COLLABORATION`，如 PROC-01）按 V9 规范裁剪，不单独建模或实现，其业务链路由 M1 状态机、M2 行为、M6 审批流和 M7 报表承载；不得新建协同流或 `SUB_FLOW_CALL` 子流程调用，该情形不属于需要暂停的模型冲突。

### 6.3 提交行为启动流程

`Contract_Submit` 行为（service）在事务内：

1. 校验规则（appliedRules）；
2. `status → 待财务经理审批`；
3. 调 `FlowEngine.start(definition_id, business_key, business_object_refs, variables, creator_id)`；
4. 把返回的 `instance_id` 回写到业务记录（`instance_id` 字段），并与当前活动联动。

> 引擎启动后，会按 start 节点的后继创建首个 `approval_task`，并通过 `role_ref` 解析出办理人（`_resolve_assignee`：查 `sys_user_role` 关联 `sys_role.code=role_ref` 的第一个启用用户）。**因此角色必须在步骤 6 已配置好、且有用户绑定，否则任务无办理人。**

### 6.4 工作台审批处理

审批人在“审批中心 → 待我审批”处理，调用 `/api/workbench/todo/{id}/approve|reject|return`，后端 `workbench_service` 在**同一事务**内：

1. 校验任务归属与状态；
2. `engine.approve/reject/return_to(...)`；
3. `sync_status_from_instance(...)` 把流程状态映射回业务对象状态：
   - 实例 `APPROVED` → 业务 `已通过`；
   - 实例 `REJECTED` → 业务 `已驳回`；
   - 实例 `RUNNING` → 按当前 TODO 任务的 `role_ref` 映射为"待 XX 审批"。

### 6.5 与流程引擎的配合点清单

| 配合点 | 做法 |
|---|---|
| 流程定义来源 | M6 → `flow_definition.node_graph`（§5.2） |
| 审批人解析 | `role_ref` → `sys_role.code` → `sys_user_role` → 首个启用用户（可扩展为多人会签/按数据范围分配） |
| 状态回写 | 引擎更新 `flow_instance.status` + `flow_task`，业务侧经 `sync_status_from_instance` 同步 `status` |
| 职责分离（禁止自批） | 仅当需求、M3 或 M6 明确定义时实现，不作为所有审批流的默认要求 |
| 通过后的联动 | 通过后若需改变业务状态/触发下游，用 M2 `syncTriggers` 或审批流末尾的 `behavior_call`/`system_task` 节点 |
| 撤回 | 仅当需求和 M6 明确定义时实现；未定义时不得因为底座存在示例能力而自动增加 |

### 6.6 审批结果

通过、驳回、退回、撤回、重新提交和禁止自批均为可选业务能力，只实现需求与 M6 明确定义的结果及状态迁移。底座已有接口或示例不得被视为当前应用必须具备的业务需求。

## 7. 右侧 AI 对话框实现指南

> 依据《AI 原生应用技术架构设计文档》第 9 章 + UI-UE 规范 §12。目标：让 AI 通过自然语义对话完成业务问答、功能导航、工具调用与只读查询。

### 7.1 架构定位

AI 编排层位于"后端服务层"之上，**复用同一套后端能力**：

```
前端 AI 对话组件 (SSE 流式渲染)
  └─ POST /api/ai/chat  (SSE)
        └─ AI 编排层 (ai/ + sse/)
              ├─ DeepSeek 客户端
              ├─ 系统提示词构建（读 Ontology Registry）
              ├─ 工具注册（导航/查询/行为/只读 SQL）
              └─ 只读 SQL 白名单控制器 (sql_readonly/)
```

### 7.2 配置大模型

大模型连接信息统一通过系统管理界面中的“配置大模型”功能维护，至少包括 Base URL、API Key 和模型 ID，并提供测试连接。配置持久化到 `ai_config` 表，读取时对 API Key 脱敏；API Key 不得写入 `backend/config.yaml`、源代码或前端资源。

### 7.3 系统提示词构建（基于本体注册表）

每次对话注入动态 system prompt，至少包含：

1. 系统角色与能力说明；
2. 可用功能/行为/查询清单（来自 `registry["behaviors"]`、`registry["query_reports"]`）；
3. 可用工具清单及调用说明（导航/查询/行为/SQL 只读）；
4. 只读安全边界（不得写数据）；
5. 渲染协议约定（何时返回 text/table/chart/action）。

### 7.4 工具注册（Function Calling）

由注册表自动生成工具 schema，分类如下（架构文档 §9.6）：

| 工具 | 来源 | 说明 |
|---|---|---|
| 页面导航 | `registry["menus"]`/`screens` | 打开某录入/查询页 |
| 查询工具 | M2 QUERY / M7 | 执行某列表查询、取详情 |
| 行为工具 | M2 COMMAND | 默认只提供能力说明或导航到固定业务页面，不在 AI 对话中直接执行写操作 |
| 图表工具 | 查询结果 | 转柱状/折线/饼图（ECharts） |
| SQL 只读工具 | `registry["db_whitelist"]` | 无现成 API 时的只读查询兜底 |

### 7.5 SSE 流式输出协议

后端 `sse/` 按以下分片推送（架构文档 §14.2）：

```
message_start → delta* → (tool_call | tool_result)* → render_payload → message_end
```

前端 `ReadableStream` 逐片读取，增量拼接文本、展示"正在查询…"状态、最终切换为结构化渲染。

### 7.6 结果渲染协议

| 渲染类型 | 触发场景 |
|---|---|
| `text` | 状态反馈、业务说明、执行结果 |
| `table` | 列表、统计、结构化查询结果（复用与固定页面同一套表格 CSS） |
| `chart` | 趋势、分布、统计图（ECharts） |
| `action` | 引导打开页面、查看详情、执行行为 |

### 7.7 安全边界（强制）

1. AI 对话默认**只读**，禁止写数据；
2. 写操作必须由用户在固定业务页面完成，AI 对话只可导航到对应页面，不直接执行新增、修改、删除、提交或审批；
3. 动态 SQL 严格只读：仅 `SELECT`、仅白名单表/字段、强制 `LIMIT`、禁多语句、执行超时、记录审计（架构文档 §10）；
4. 所有工具调用记录审计日志（`audit_logs`）。

### 7.8 前端 AI 对话组件

将 `AdminLayout.tsx` 中右侧占位替换为真实对话组件：

- 消息区：用户右对齐品牌蓝底白字、AI 左对齐白底（UI-UE §3.4）；
- 输入区：圆角 textarea + 品牌蓝发送按钮；
- 支持 `text/table/chart/action` 四类渲染，表格/状态标签复用全局 CSS 类。

## 8. 其它补充约定

1. **可追溯门禁**：M2 中 `triggerType=USER_ACTION` 的行为必须被至少一个 MU 操作功能点引用；MU 引用的行为必须存在（框架 §1.3.7）。
2. **一致性约束**：M2 `queryReportRef` ↔ M7 `behaviorRef` 严格一对一；M6 的 `roleRef`/`behaviorRef`/`subFlowRef` 必须引用存在的模型元素。
3. **事务边界**：一个行为只改一个聚合（聚合内主从同事务）；跨聚合靠 syncTriggers 或流程编排。
4. **逻辑删除**：所有业务数据删除用 `flag=0`，历史保留；被引用的主数据不可删只能停用。
5. **状态机**：对象状态迁移严格按 M1 `lifecycle` + M2 postconditions + M6 结果，不出现模型外状态。
6. **版本管理**：模型文件内维护 `version`，破坏性变更记录 `CHANGELOG.md`。
7. **审计**：关键写操作与 AI 工具调用写入 `audit_logs`。
